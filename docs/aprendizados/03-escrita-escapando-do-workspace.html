Aprendizado 03

Escrever arquivo escapava do workspace

Ler um arquivo funcionava. Escrever, no mesmo diretório, era recusado com "path is outside the authorized workspace" — sendo que estava dentro. E o mesmo defeito, visto pelo outro lado, deixava uma escrita cair fora da raiz autorizada.

O sintoma

Num workspace legítimo, read_file e directory_tree respondiam normal. write_file e create_directory falhavam com SecurityException, apontando um caminho que visivelmente estava dentro da raiz registrada.

A causa raiz

A raiz é registrada com toRealPath(), que resolve link simbólico. Mas um arquivo que ainda não existe não pode ser resolvido — só normalizado:

Path target = Paths.get(path).toAbsolutePath().normalize();
if (Files.exists(target)) {
    return target.toRealPath();   // arquivo existente: link resolvido
}
return target;                    // arquivo novo: link NÃO resolvido

No macOS, /tmp e /var são links para /private/.... A raiz virava /private/var/.../projeto e o arquivo novo continuava /var/.../projeto/novo.txt. O prefixo nunca casava.

O lado grave é o inverso. Um link dentro do workspace apontando para fora era aceito para arquivo novo: o caminho textual começava com a raiz, a verificação passava, e a escrita ia parar do lado de fora. Um agente que cria arquivos podia escrever fora da área autorizada.

Como foi resolvido

Resolver o ancestral existente mais próximo e reanexar o resto. A verificação passa a comparar por onde a escrita realmente vai cair, não por como o caminho foi escrito.

Cinco testes cobrem os dois sentidos. Um detalhe quase enganou: o teste do escape passava mesmo com o bug, porque o @TempDir vive sob /var e a recusa vinha pelo motivo errado. Foi preciso resolver o diretório temporário primeiro, para isolar o link deliberado.

Lição: um teste que passa nos dois estados não protege nada. Desligue o conserto e confirme que ele falha.
