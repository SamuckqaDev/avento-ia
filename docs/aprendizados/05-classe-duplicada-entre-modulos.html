Aprendizado 05

A ferramenta existia, o despachante não a conhecia

O agente respondia "Tool not found" para uma ferramenta registrada, documentada e exposta ao modelo. A ferramenta existia. O despachante é que não a conhecia.

O sintoma

Chamar schedule_task devolvia Tool not found or server disconnected, apesar de a ferramenta estar em LocalToolNames, ter executeScheduleTask implementado e aparecer no schema enviado ao modelo.

A causa raiz

Existiam duas classes com o mesmo nome totalmente qualificado:

avento-agent/.../com/avento/service/tools/LocalToolNames.java   (42 nomes)
avento-mcp/.../com/avento/service/tools/LocalToolNames.java     (41 nomes)

Diferiam por exatamente uma entrada: schedule_task. Mesmo pacote, mesmo nome, dois jars — quem vence é a ordem do classpath. Na aplicação montada venceu a cópia defasada.

Nada avisa sobre isso. Não é erro de compilação, a IDE não reclama, os testes passam. O único sinal era um erro de runtime que parecia problema de MCP.

Como foi resolvido

avento-agent depende de avento-mcp e não o contrário, então a cópia do mcp é a legítima: schedule_task foi para lá e a duplicata saiu.

A varredura em busca de outras encontrou mais 22 nomes duplicados entre módulos, na maioria DTOs entre avento-media e avento-workspace. Todas ainda idênticas — inofensivas hoje, mas a mesma mina.

NoDuplicateClassNamesTest não proíbe duplicar; proíbe divergir. Editou uma cópia e esqueceu a outra, o build quebra. Unificar as 22 continua sendo dívida legítima; o teste segura a ponte até lá.

Descartado no caminho: o banDuplicateClasses do enforcer pega o mesmo problema, mas arrasta colisões de terceiros (commons-logging contra spring-jcl) que exigiriam uma lista de exceções para manter viva.
