Aprendizado 06

O gateway rodava uma flag que não existe

O Docker MCP Gateway — o servidor que agrega os outros em containers isolados — nunca subiu. Por dois motivos empilhados, e o de baixo escondia o de cima.

O sintoma

O gateway aparecia no catálogo como indisponível, com a mensagem "Configure AVENTO_MCP_DOCKER_GATEWAY_PROFILE". Configurar não resolvia.

A causa raiz, em duas camadas

Primeira: o perfil nunca era definido em lugar nenhum, então o catálogo devolvia indisponível antes de tentar qualquer coisa. Falha silenciosa — nada no log.

Segunda: e se fosse definido, quebraria mesmo assim. O comando era

docker mcp gateway run --profile <perfil>
→ unknown flag: --profile

Essa flag não existe no CLI do Docker MCP Toolkit. As reais são --servers e --enable-all-servers.

O teste de integração ao lado já usava --servers, a flag correta. Quem o escreveu sabia. Mas ele está atrás de uma variável de ambiente e nunca rodou, então código de produção e teste divergiram sem ninguém notar.

Um terceiro detalhe, de desenho

O gateway tinha gatilho de intenção nas palavras docker, dockerfile, container. Isso é o contrário do propósito: ele não é ferramenta sobre Docker, é o transporte que serve os outros servidores. Falar de Dockerfile subia o gateway à toa; precisar de um servidor agregado nele não disparava nada.

Como foi resolvido

Comando corrigido, gatilho removido, e a configuração mudou de forma: vazio deixou de significar "desligado" e passou a significar "os servidores habilitados no Docker Desktop".

E uma limitação que não é config e precisa estar escrita: o docker mcp é um plugin que vive dentro do Docker.app e fala com o backend do Desktop, não com o daemon. Sob Colima, OrbStack ou Rancher os containers rodam normalmente e o plugin responde "Docker Desktop is not running" até no --dry-run. Agora o catálogo diz isso em vez de vazar um "comando não encontrado" que é falso.

Lição: teste atrás de flag que ninguém liga é documentação, não proteção.
