Trocar o modelo no seletor não trocava nada

Trocar o modelo no seletor do cabeçalho não trocava nada. A escolha chegava ao backend e era descartada no caminho, sem aviso.

O sintoma

Duas linhas seguidas no log, com 79 milissegundos de diferença:

run starting for chat 2 with model granite4.1:8b   ← a escolha chegou
Agent round 1 starting build for model qwen3.5:9b  ← rodou outro

A causa raiz, de novo em duas camadas

Um literal escondido num serviço:

return activeKind(userId) == OLLAMA
    ? readSystemField("defaultModel", "qwen3.5:9b")   // ← chumbado
    : "";

Com a tabela de provedores vazia e o Redis sem o campo, isso devolve o literal. Contradiz o avento.agent.default-model: granite4.1:8b e, pior, nunca deixa o método devolver vazio — sempre existe um "modelo configurado".

Uma heurística que confunde escolha com ausência:

if (!configured.isEmpty() && requested.equalsIgnoreCase(defaultChatModel))
    return configured;   // ignora o seletor

Escolher granite4.1:8b — que é o default — era lido como "não escolheu nada", e o literal vencia. Os dois defeitos precisavam se encontrar, e encontraram: sozinho, nenhum dos dois causaria o sintoma.

Como foi resolvido

O literal virou "" — sem escolha gravada, quem decide o padrão é quem chama, igual aos acessores vizinhos que já faziam certo. E só pedido em branco conta como "não escolhi", que é o que o front manda enquanto o seletor não foi tocado.

A decisão saiu para ModelNames.chooseChatModel, função pura com seis casos cobertos.

Antes disso eu afirmei que o seletor funcionava, deduzindo da tabela vazia sem testar o caminho todo. O log provou o contrário. Lição: dedução sobre estado de banco não substitui olhar o que o sistema fez.
