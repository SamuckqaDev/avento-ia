Learning 11

A test passed in an order production never has

The suite was green, including the test written for the bean in question. Yet Redis reported one index through FT._LIST while settings asked for another model. The test had proved an order that production never uses.

Symptom: one configuration, another reality

FT._LIST named an index that did not match the configured embedding model. This was especially deceptive because a focused context test was already green. It looked like a Redis configuration defect, but the configuration bean was not present in the production context at all.

What made it expensive: the test asserted the intended wiring. The live application exposed the wiring that Spring had actually evaluated.

Cause: conditional configuration ran too early

A component-scanned @Configuration carried @ConditionalOnBean(JedisConnectionFactory.class). The factory is supplied by DataRedisAutoConfiguration in Boot 4.1, not RedisAutoConfiguration. Boot processes that auto-configuration after user configuration, so the condition was false when it mattered and the bean never entered the context.

Fix: let the test use Boot's order

@ConditionalOnBean is reliable in auto-configuration classes, where Boot can order conditions against their prerequisites. A context test must likewise bring the real auto-configuration in with AutoConfigurations.of(...), instead of planting the dependency by hand before the configuration under test.

A test dependency is not neutral. Its registration order can become the behavior the test accidentally validates.

The lesson

The first version of this defect hid behind a mock; the second hid behind bean ordering. In both cases, the suite asserted intention rather than reality. For conditional Spring wiring, test the auto-configuration path production takes, including its order.
