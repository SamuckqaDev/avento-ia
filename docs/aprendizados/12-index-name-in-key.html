Learning 12

Putting the index name in the key stranded 5,240 chunks

Naming an index after its model sounded like isolation. Instead, Redis held 10,517 vector keys while 5,280 were live, and two indexes reported the same count as they climbed together.

Symptom: the same content was retrievable twice

After the index was renamed, the live count was 5,280 but the vector-key count was 10,517. Two RediSearch indexes each reported the same growing total. Nothing crashed; the duplicate content quietly consumed places in top-k results and cut their diversity in half.

ObservedExpectedMeaning
10,517 vector keys5,280 live chunksOld chunks had been abandoned.
Two indexes, matching countsOne active indexBoth indexes watched the same keys.

Cause: two mistakes compounded

The manifest key included the index name. Renaming the index therefore changed the address at which the old manifest could be found; its listed chunks became unreachable. Chunk IDs also derive from the project key, so the next pass wrote new keys instead of overwriting the old ones.

Index name changes
The manifest key changes too.
→
Old manifest is lost
The cleanup list cannot be read.
→
New chunks are written
The old vectors remain in Redis.

Meanwhile, both RediSearch indexes were defined over the same avento: key prefix. An index name is only the name of the index definition; it does not isolate the data keys. The retired index kept indexing everything the new pass wrote.

RediSearch rule: an index is defined over a key prefix. Rename an index while sharing the prefix and both definitions still see the same documents.

Fix: one root, one manifest

The manifest key went back to being only the project root. Its indexName now lives inside the manifest. On an index change, the indexing pass can still find the old manifest, delete each chunk it lists, and then rebuild the project into the new index.

Identity belongs in the stable key; mutable placement belongs in the record stored at that key.

The lesson

Renaming an index isolates nothing while its data keys are shared. Keep one manifest per root, carry the index name as manifest data, and make cleanup read the previous state before writing the next one.
